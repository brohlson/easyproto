# Publish complete project revisions through a pointer

The project folder contains `project.json`, optional project-relative `assets/` and managed `.easy-proto/<snapshot UUID>/` directories. Each snapshot contains a schema-versioned manifest, real UTF-8 HTML/CSS files with relative references, and the project-scoped command ledger. Source checksums catch managed files changed on disk. The running app owns the managed files and expects one writer. The standard desktop profile enforces a single app instance. Keep one writer when launching isolated development profiles, and avoid editing the folder while a writer is active. Filesystem races with another local process that already has write access to the project are outside the contract.

The service serializes commands within the open project. It writes and flushes the new snapshot files and temporary pointer before atomically renaming that pointer over `project.json`. The rename is the commit point on a local filesystem supporting atomic same-volume rename. Acknowledgment and canvas notification follow publication. Restart loads only the named revision. An interruption before rename can leave orphan files. An interruption after rename recovers the published revision even when the application had no chance to answer. An invalid, unsupported or missing pointer with existing revision data requires recovery. The app leaves the files intact. This slice verifies process termination on the target Mac. Directory metadata durability across power loss and automatic orphan cleanup are pending.

Deduplication covers every committed ID in the lifetime of the intact project ledger. Retries compare the normalized complete command envelope, including the original expected revision, and return the original result before checking for staleness. Different inputs using the same ID conflict. Failed commands consume no ID. There is no pruning in this slice. The 32 MiB manifest ceiling ends new writes with a save failure while existing committed outcomes remain available. Every snapshot currently stores complete sources and a ledger copy, so projects grow as edits accumulate.

The desktop's duplicate command copies the selected artboard's committed source and viewport into a new artboard with its own ID and source files. It saves the copy and its offset in one revision. It uses the same command ledger and keeps the project asset namespace shared.

Copy snapshots the selected artboards' committed source and layout in memory for the open project. The system clipboard carries an opaque token. Paste uses that token to locate the snapshot and creates new boards through the same command service. Opening another project or reopening the same one clears the copy.

Undo and redo cover the last 50 committed artboard, page, and token mutations in the open project, including MCP edits. Project naming and canvas navigation have separate lifecycles. Undo and redo publish new revisions, preserve IDs on restoration, and update their in-memory stacks after a successful save. A new mutation clears redo. The first delete, undo, or redo writes schema version 2, which allows historical command results to refer to a removed artboard. Easy Proto still reads version 1. Older builds refuse version 2 projects. Reopening preserves the resulting document and command ledger and starts a fresh undo history.

MCP Undo requires a new request command ID, the expected project revision, and the original command ID of the edit to reverse. The document service checks the revision and the top undo entry in its serialized command queue. Undo and redo carry the edit’s identity between the two session stacks. Exact retries use the ordinary durable receipt, including after reopening.

Delete removes the artboard and its source from the active snapshot. Undo restores its ID, source, bounds, and place in the artboard order. The restored preview uses a new revision. Earlier saved snapshots retain their original files.

A group move, duplicate, paste, or delete publishes a single revision and takes one undo step. A move or copy adds the same offset to every selected board. The first result that affects multiple artboards upgrades the active pointer and manifest to schema version 3. The command result retains `artboard` and adds `artboards` in document order. Retrying the original command returns that full result, including after reopen. Builds from before group editing refuse version 3 projects. Selection and camera state stay in the renderer.

A batch artboard update takes an explicit list of unique IDs with a patch for each. The command service checks the expected revision and validates the complete selection before starting activity or saving. It applies patches by ID in document order, skips matching targets, and records the changed boards as one history entry. A stale revision, a missing board, or an entirely unchanged selection leaves the document and undo history intact. The existing group receipt, pointer publication, and SQLite transaction formats cover batch updates. Exact retries replay the original receipt even after Undo or reopen.

## Pages

Versions 1 through 3 open with an implicit Page 1 whose stable ID is derived from the project ID. The first page creation or rename publishes version 4 via the existing pointer swap. Version 4 stores an ordered page list and default page ID in `pageLayout` and a `pageId` on each active artboard. Later saves retain explicit page membership, including undoing the creation of the last added page and upgrading to version 5. Keep a copy of the earlier pointer and its named snapshot when opening the project in an older build. Opening a legacy project requires no rewrite.

Page creation, renaming, deletion and moving selected boards between pages are document commands. Rename preserves the page ID, position in the list and artboard memberships. Undo restores the previous name and redo restores the new one. A move changes only page membership and takes one undo step. Page creation undo removes the page and redo restores the same ID. Historical command receipts keep their original shapes. Page-only results use `page`, and historical receipts can reference pages that were subsequently undone or deleted. The selected page, selection, and camera are session state. Project-wide MCP lookup and capture still use artboard IDs. Create requests that omit a destination use the current default page.

`delete_page` removes a page and its artboards in one revision, returning a page receipt. The final page cannot be deleted. Deleting the default assigns the next page in order, or the preceding page when deleting the last entry. Undo restores page order, the previous default, artboard IDs, source bytes and geometry together. Restored artboards receive the undo revision as their source revision so the previews reload. Tokens and shared project assets remain project-wide. Existing version 4 and 5 manifests represent this state without a schema upgrade. Both folder and SQLite commits retain the deletion receipt for exact retry after reopening.

Assets are read into memory at open through allowlisted project-relative paths. Copy the optional assets directory with the project. Capture identity separately includes the digest of those asset bytes, so the same document revision opened with different asset bytes has a different render identity.

## Project tokens

The first token edit publishes schema version 5 with the page layout and two managed files in the same atomic snapshot. `design.tokens.json` is the DTCG source and `tokens.css` is the exact generated CSS. The manifest records both digests, and the token command ledger stores digests as the result. Undo and redo restore the committed pair. Older projects open with an empty token dictionary and upgrade on their first token edit. Version 5 continues after undo. A build that reads through version 4 requires an earlier pointer and its snapshot to open a recovery copy.

The initial DTCG profile supports named groups, inherited types, sRGB colors, pixel and rem dimensions, numbers, font families with bounded ASCII names, numeric font weights, ms and s durations, and whole-token aliases. Style Dictionary receives validated data and a fixed configuration. Descriptions and extensions stay in the JSON. Preview HTML links the exact generated stylesheet before the artboard CSS through its existing isolated origin. Live identity includes the CSS digest, and capture uses the stylesheet from the requested snapshot.

The dictionary supports up to 256 tokens and 128 KiB each for the JSON and CSS. Lowercase path segments join with hyphens and an `--ep-` prefix. A flattened name collision rejects the edit, as do malformed documents and unresolved aliases. Keep variable names stable when editing values. New CSS bytes update every preview URL while edits that only change metadata keep preview identity. Capture checks that the pinned stylesheet loaded and reports both token digests with the document and source revisions.
