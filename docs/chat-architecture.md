# Local agent chat architecture review

## Decision

Put a project chat dock in Easy Proto's trusted window. It will talk to an installed agent runtime through a provider adapter owned by Electron's main process. The app will create its own agent sessions so conversations can resume using a supported session ID. Connecting to a running desktop conversation is outside the first slice and would require a documented API and a separate authorization flow.

Start with Codex App Server over private stdio. Qualify the exact release and authentication path before making the provider available. Give the first real turn an explicit attachment and let it return a typed artboard edit proposal. Show the HTML/CSS changes and require an Apply action. An accepted proposal goes through the existing revision-checked document command service, so a human can undo it in one step. Give chat a private tool broker only after testing its project authority. The external MCP workflow continues to be available for an agent the user starts in their terminal.

## Ownership and data flow

1. The dock shows a provider, conversation, composer and attachment chips. Clicking Send freezes the project instance and activation, target page and artboard IDs, source and document revisions, and the exact approved HTML, CSS or screenshot data. Main materializes these from its committed snapshot after validating sizes and scope. Page or selection changes affect the next turn's attachments.
2. The existing isolated preload exposes a narrow API for chat state, starting a turn, stopping a turn, and deciding a proposal. Main validates the sending frame, ownership, request types and payload limits. It owns the turn state machine and manages the runtime using private pipes from an app-owned working directory. The executable never receives the project folder as its working directory. A dedicated utility process is an option for isolating the adapter's parsing workload. The capability check still belongs to main.
3. Adapters translate provider messages into bounded typed events with conversation ID, turn ID, activation and monotonic sequence. Start with text batch, proposal, receipt, failure and terminal state. Main owns the authoritative state and offers a bounded snapshot on reconnect so the renderer can recover gaps. Close a turn on a single terminal event and ignore old-sequence or wrong-activation notifications. Stderr stays separate and redacted. Set frame, prompt, attachment, output, startup and interrupt limits before enabling a real runtime.
4. A proposal carries a stable ID, selected artboard ID, base revision and a bounded HTML/CSS patch. Main renders the review contents from validated data and assigns the command ID. Apply checks the active instance and expected revision at admission, rejects a stale preview, and calls the existing command service at most once per accepted proposal. A retry of an accepted proposal reuses the same command ID. A saved edit, preview update and captured image have separate status. Capture describes its project revision, artboard source revision and token digests.
5. Stop, project switch, Home, close, lost authorization and provider exit revoke the turn's capability synchronously. Interrupt the run and reap it and its process group on a bounded deadline. A command already admitted to the document queue may commit. Show its revision and leave it in normal undo history. After the process exits unexpectedly, show whether the outcome is known, recover the recorded receipt if one exists, and let the user choose whether to send another message.

[Electron utility processes](https://www.electronjs.org/docs/latest/api/utility-process) · [Node child-process lifecycle](https://nodejs.org/api/child_process.html)

## Security review

| Finding | Disposition and required evidence |
| --- | --- |
| Critical cross-project authority risk | The existing external bearer permits discovery of the current project through `get_context`. The embedded runtime receives neither that bearer nor the unrestricted endpoint. Start with a brokerless proposal flow. For future agent tool calls, issue a short-lived capability bound to the opened project instance, its activation and a single turn. Validate it at queue admission and restrict tool names, artboard IDs and payloads. Test two folder copies with the same project ID, switch during a pending call, check queued versus admitted work, and verify that Stop revokes access before its interrupt completes. Security and Architecture own the gate. |
| Major tool and runtime escape risk | Start the provider without a shell via an absolute trusted path, a constrained subprocess environment and an app-created working directory. Disable shell, file, network tools, web search, connectors, plugins and inherited MCP servers through the provider's supported configuration. A provider sandbox labeled read-only can still permit broad file reads. Confirm actual isolation with a synthetic fixture. On Claude, an allow list can grant permission without removing other tools. Verify available tools directly and require isolated settings. Unknown requests fail closed. Security and Infrastructure own the gate. |
| Major provider output and data exposure risk | Treat HTML, screenshots, model text, stderr and tool results as untrusted inputs. Render text or a restricted Markdown subset with no raw HTML, remote images, auto-navigation or arbitrary embedded links. Retain the artboard iframe boundary. Present approval UI only from validated proposal events. Keep provider credentials, prompts and full project paths out of diagnostic logs. Verify that provider traffic contains only user-approved attachments and redacted diagnostic output. Security and Frontend own the gate. |
| Major distribution and entitlement risk | Record supported executable versions and auth modes, and exercise Finder launch of a signed/notarized Apple Silicon build. Cover missing binary, binary replacement, deprecated protocol, expired credentials and restricted workspace plans. Qualify process cleanup from the packaged app. Infrastructure owns the gate and checks current terms for each provider before shipping its adapter. |
| Major commit and lifecycle ambiguity | Fake provider tests must cover malformed streams, duplicate events, stuck helpers, cancel during setup, stale revisions, window reload, bounded output and a lost response after an accepted command. Keep the original command ID until the receipt is reconciled. Architecture owns the gate. |

Agent attachments and provider-created proposals are data. Do not derive project permissions from prompt instructions, output, a conversation ID, or the portable project ID alone. Keep proposed edits scoped to existing artboard HTML/CSS in the first provider experiment. Project tokens, file access, shell commands, and automatic document mutations require separate product approval and security evidence.

## Interface and history

Use the upper-right Chat button to show or hide the dock and indicate when it is active. Place the dock beside the canvas with standard desktop focus behavior. Keep the composer pinned to the bottom while the conversation and proposals scroll above it. At narrow window sizes it may overlay the canvas without changing its zoom. Keep an active turn visible when the dock is reopened, and keep its pending approval separate from canvas selection and artboard activity. Batch incoming text and announce status changes to assistive technology. Preserve scroll when a user reads older messages and keep Stop keyboard accessible. Escape closes a menu or returns focus to chat, and switching the project cleanly disposes its pending state. Dogfood both themes, panel widths around the minimum window size, keyboard navigation, and VoiceOver with a fake stream before connecting a provider.

Default to session-only transcripts for the experiment. If we add history, store it under app data, outside the portable project. Key records by canonical project instance and provider, keep opaque provider session IDs, use bounded retention and explicit Clear history, and distinguish clearing the local copy from deleting a provider session. Avoid duplicating the provider's complete persisted history. Provider retention follows the user's provider account and the configured runtime.

## Review evidence and build order

Architecture and Reliability, Security, Infrastructure, and Frontend with Design covered the current Electron, MCP and document boundaries in independent read-only consultations. Security's proposal-first recommendation is the initial integration decision. Infrastructure found a Codex CLI from a desktop bundle on the development shell and no Claude CLI on that shell's PATH. That is discovery evidence. Neither runtime connection, login, packaged-app launch, nor runtime isolation was tested for this review.

1. Dogfood a chat dock in EasyProtoMocks, including context attachment, Stop, Apply and conflict states. Build it with a fake streaming provider and a deterministic, single-artboard proposal. Exercise stale scope, commit, receipt, and undo without starting any provider.
2. Run a Codex qualification spike using one synthetic artboard on Apple Silicon. Pin a supported release, verify auth and process policy, record actual context sent, confirm Stop/reap and apply/undo, then check the packaged build. Keep the user in control of what gets sent and applied.
3. Qualify Claude independently through the documented SDK auth path. Add scoped agent tools only after both scope isolation and real provider behavior have evidence. Keep unresolved critical and major findings as release gates.

The desktop now implements the first slice as **Local demo**. A user can attach one artboard, request a headline change, and review the streamed proposal before applying it. The document command records the accepted edit in project undo history. The desktop check covers a stale project revision, retired project access, repeated Apply, and the race found in specialist consultation where Stop arrives after streaming has finished. ## Opt-in Codex experiment

Desktop developers can explicitly select a local executable and provide a dedicated OpenAI API key through the launch environment. The temporary Codex profile uses a Responses provider pointing at the OpenAI API. Easy Proto does not read the user's existing Codex profile. The app checks the qualified version before starting a turn. The normal launch keeps the local demo. [Launch instructions](../readme.md#try-the-chat-drawer) · [Codex provider configuration](https://learn.chatgpt.com/docs/config-file/config-reference)

The provider receives the user's prompt and up to 160 characters of plain text from the attached artboard's first editable heading. Codex adds runtime metadata for its temporary workspace. Project paths, HTML, CSS, tokens, credentials, and the MCP bearer stay out of the model input. The dedicated API key authorizes the HTTP request. The adapter uses one ephemeral thread per request, refuses unexpected server-initiated requests, and limits time and output. It accepts a typed plain-text reply and replacement. The desktop applies the replacement through the existing revision-checked document command only after review.

The installed-build check ran real Codex App Server against a loopback Responses fixture and verified the outbound input, tool list, malformed proposal rejection, and Stop. The only tool advertised in the fixture request was `request_user_input`, which the adapter rejects if invoked. Electron exercised the same provider in a disposable project and checked the rendered heading before Apply, after Apply, and after Undo. Run this check with `EASY_PROTO_CHECK_CODEX_BIN="$(command -v codex)" pnpm verify`. Live paid inference, other Codex versions, packaged builds, and Claude remain open. [Synthetic turn and desktop verification](../evidence/codex-compatibility/turn.log)

## Sign in with ChatGPT

The local desktop has a separate **Continue with ChatGPT** connection. Main discovers the installed Codex and checks the qualified version before opening the system browser. OAuth uses OpenAI's dynamic client registration, a stable per-installation host ID, an expiring IPv4 loopback listener, PKCE, state, and a JWKS-verified ID token with issuer, audience, expiration, nonce and subject checks. The active account's issued client ID and subject stay bound. The first slice remembers one account. [OpenAI registration and sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in)

The main process encrypts the credentials with Electron safe storage and atomically writes the record in the app profile. The renderer sees the connection state and account label. Main serializes credential writes and token rotation. Disconnect stops active ChatGPT work, discards unaccepted proposals, attempts to revoke the refresh token, and clears local credentials. The account record stays associated with its issued client and host. The browser sharing app has its own access system. [OpenAI account and session contract](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions)

Before a model turn, main verifies the granted plan scopes, refreshes the access token when needed, and selects an eligible returned model. The OAuth access token reaches the installed Codex child in its scoped environment. Its temporary profile, isolated working directory, fixed public Responses endpoint, and approval-only project edit path remain in use. [OpenAI Codex App Server configuration](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server)

The automated OAuth fixture covers mismatched and duplicate callback state, PKCE, the ID token, declined plan usage, changed account identity, rotating-token serialization, restart, and disconnect. The installed Codex fixture verifies streamed HTTP with `store: false`, the structured proposal, cancellation, Apply, and Undo. `node verify/chatgpt-live.mjs` uses a disposable Electron profile and waits for browser consent before making a real turn. [Fixture checks](../evidence/chatgpt-sign-in/fixture.log)

The live Apple Silicon macOS run verified browser consent, plan-backed inference through the installed Codex, a review that preserved revision 0, Apply at revision 1, and Undo at revision 2. Test setup discarded the disposable project and its local profile. [Live result](../evidence/chatgpt-sign-in/live-turn.json)

## Home agent profiles

Home is the settings surface for connections and the only view permitted to change them. Multiple named Codex and Claude profiles share an encrypted, versioned local settings file. Each profile has a stable ID. Codex keeps its own issued registration, grant, and reconnect identity for each profile, using one stable Easy Proto installation ID. On first launch with the previous single-account settings, the app imports that account as **Codex**. The previous encrypted file is retired after the new settings are saved. Claude stores a verified Anthropic API key and selected model for each profile. Neither provider's credentials are included in the project folder or renderer status.

The chat picker keeps its last selection for each project in the current app session. Conversation display is scoped to the local folder and project ID, then to the selected profile. Reopening a project restores its selection and recent display history while the app is running. Both providers receive one prompt and the attached headline per request. Conversation display history is local and is not supplied to later turns. The approval is bound to the active project and source revision. Leaving the project cancels unresolved work.

Claude runs the installed CLI in a temporary directory using a clean environment and explicit restrictions on built-in tools, MCP configuration, browser integration, and session persistence. Easy Proto verifies a minimum CLI version, then validates the provider's result before showing an edit proposal. The Anthropic credential is sent to Anthropic for verification and supplied to the runtime for the selected profile's turn.
